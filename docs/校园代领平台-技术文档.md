# 校园帮帮 — 技术文档

> **版本**: 4.0 | **更新日期**: 2026-09-30 | **技术栈**: React 18 + Spring Boot 3.3 + MySQL 8 + Redis 7 + Kafka + Elasticsearch 8 + DeepSeek

> **v4.0 相对 v3.0 的主要变更**
>
> - 后端重建为**事件驱动架构**：订单事件与业务数据同事务写入 Outbox，再由 Kafka 分发到 5 个独立消费者组
> - 新增 **Elasticsearch**：带权重全文检索、地理查询、BI 看板聚合
> - 新增 **Redis 缓存体系**：Cache-Aside 分级 TTL + 事务提交后失效
> - 认证改为 **JWT + 三角色 RBAC**，含登录失败锁定与 token 版本号撤销（替代原先的明文密码比对）
> - 数据库改由 **Flyway** 版本化迁移，`sql/init.sql` 已删除
> - v3.0 中的 `8088` 后端端口、明文密码存储、轮询刷新等描述**均已更正**

## 一、项目概述

校园帮帮是一个前后端分离的校园代领平台，学生可下单委托跑腿员代取外卖/包裹，跑腿员接单配送，管理员全盘管理。

后端核心链路是**事件驱动**的：订单状态变更不直接发消息，而是与业务数据同事务写入 `event_outbox` 表，由独立调度器轮询投递至 Kafka；5 个消费者组（通知推送 / ES 同步 / 自动派单 / 异常检测 / 审计日志）各自全量消费，互不干扰。

### 三角色权限矩阵

| 功能 | 学生 (STUDENT) | 跑腿员 (RUNNER) | 管理员 (ADMIN) |
|------|:---:|:---:|:---:|
| 新建订单 | ✅ | — | — |
| 查看订单列表 / 详情 | ✅ (自己的) | ✅ (自己的配送) | ✅ (全部) |
| 取消订单 | ✅ (待接单时) | — | ✅ (非已完成 / 已取消) |
| 确认收货 | ✅ | — | — |
| 评分跑腿员 | ✅ | — | — |
| 浏览可接订单 | — | ✅ | — |
| 接单 / 取件 / 送达 | — | ✅ | — |
| 收入统计 | — | ✅ | — |
| 跑腿员管理（新增 / 编辑 / 停用） | — | — | ✅ |
| 学生用户管理 | — | — | ✅ |
| 后台流水 | — | — | ✅ |
| 数据看板 / BI 聚合 | — | — | ✅ |
| 全文检索 / 附近订单 | — | — | ✅ |
| 异常预警 / AI 助手 | — | — | ✅ |
| 手动触发派单 | — | — | ✅ |
| 登出（撤销自己的全部 token） | ✅ | ✅ | ✅ |
| 踢下线（撤销他人全部 token） | — | — | ✅ |

> **权限不是前端隐藏菜单实现的**：`config/SecurityConfig.java` 用路径矩阵强制角色（表见 5.0 节），
> 另有按对象归属的二次校验——例如订单详情只有下单学生、接单跑腿员与管理员能看，不是「登录了就能看」。
>
> ⚠️ **全文检索目前仅管理员可用**（`/api/search/**` 在路径矩阵里归 ADMIN）。学生与跑腿员的订单页走
> `/api/orders` 的条件筛选。如果希望学生也能搜自己的订单，需要放开这条规则并加上按 `studentId` 的过滤。

## 四、数据库设计

### 表清单（13 张）

**业务表（V1 基线，11 张）**

| 表名 | 说明 | 主要字段 |
|------|------|----------|

| `runner` | 跑腿员 | id, runner_no, name, phone, id_card, password(BCrypt), status(0空闲/1接单中/2休息), rating, completed_orders, max_concurrent |
| `order_info` | 订单 | id, order_no, student_id, runner_id, order_type, title, pickup/delivery_location, pickup_lat/lng, delivery_lat/lng, amount, tip, packages(JSON), pickup_code, status, completed_at |
| `order_tracking` | 订单轨迹 | id, order_id, status_from, status_to, description, operator_id, operator_type |
| `payment` | 支付记录 | id, payment_no, order_id, payer_id, payee_id, amount, pay_status, pay_channel, transaction_id, paid_at, settled_at |
| `review` | 评价 | id, order_id, reviewer_type(1学生/2跑腿), rating(1-5), content, tags |
| `notification` | 通知消息 | id, user_id, user_type, notify_type, title, content, related_order_id, is_read |
| `ai_chat_history` | AI 对话 | id, session_id, user_id, user_type, role, content, intent, token_count |
| `anomaly_alert` | 异常预警 | id, target_type, target_id, anomaly_type, severity, description, ai_analysis, is_resolved |
| `delivery_distance_matrix` | 配送距离矩阵 | id, pickup_location, delivery_location, avg/median/min/max_minutes, order_count |
| `pricing_rule` | 定价规则 | id, name, condition_type, condition_expr, price_factor, is_active |

**事件表（V2 迁移，2 张）**

| 表名 | 说明 | 主要字段 |
|------|------|----------|
| `event_outbox` | 事务事件发件箱 | id, event_id, aggregate_type, aggregate_id, topic, event_key, payload(JSON), status(PENDING/SENDING/SENT/FAILED/DEAD), retry_count, next_retry_at, error_message, sent_at |
| `processed_event` | Kafka 消费者幂等记录 | **(event_id, consumer_name) 联合主键**, processed_at |

> **为什么幂等键是联合主键**：同一条事件需要被多个消费者组各自消费一次，
> 只用 `event_id` 会让第二个消费者读到重复键而误判为「已处理」。

**索引（V3 迁移）**：为订单列表、跑腿员收入、待接单池、今日完成、派单候选、告警概览补齐复合索引，
并**删除被最左前缀完全覆盖的冗余单列索引**（留着只增加写入成本）。详见 `V3__performance_indexes.sql` 内的逐条注释。

### 订单状态流转

状态机的合法转移在 `common/StatusFlowValidator.java` 中集中定义：

| 当前 | 可转移到 | 说明 |
|:---:|:---:|---|
| 0 待接单 | 1, 6 | 跑腿员接单，或学生取消 / 管理员强制取消 |
| 1 已接单 | 2, 3, 6 | 取件中（2）或直接配送中（3） |
| 2 取件中 | 3 | 保留的中间态 |
| 3 配送中 | 4 | 确认送达 |
| 4 已送达 | 5 | 学生确认收货 |
| 5 已完成 | — | 终态 |
| 6 已取消 | — | 终态 |

```
 学生创建 (0 待接单) ──(学生取消 / 管理员强制)──▶ 6 已取消
      │
      │ 跑腿员接单（CAS 绑定 runnerId，冲突返回 409）
      ▼
   1 已接单 ──▶ (2 取件中，可选) ──▶ 3 配送中
      │                                │
      └────────────────────────────────┘
                                       ▼
                            4 已送达 ──(学生确认收货)──▶ 5 已完成 ──(学生评分)──▶ 重算 runner.rating
```

> ⚠️ **v3.0 说「跑腿员取件直接跳到 3，跳过 2」不准确**：`1 → 2 → 3` 与 `1 → 3` **都是合法转移**，
> 状态 2（取件中）在状态机里是一等公民；前端「待取件，开始配送」按钮走的是直连路径 `1 → 3`，
> 所以实际链路里很少看到 2，但它不是非法状态。

## 五、API 接口文档

### 5.0 基础规范

- 统一响应：`{ code: 200, message: "操作成功", data: {...} }`；失败时 `code` 为 4xx/5xx 且 `data` 为 `null`
- 认证：除下表标注「公开」的接口外，均需 `Authorization: Bearer <token>`；
  未认证返回 **401**，已认证但角色不足返回 **403**
- 分页参数：`?page=1&size=10`（`size` 上限 100，`size<=0` 会被拒绝而不是退回全表）
- **操作者身份取自 token，不是请求体**——客户端无法伪造 `operatorId` / `studentId`

**按路径的角色限制**（`config/SecurityConfig.java`，自上而下匹配）

| 路径 | 规则 |
|---|---|
| `OPTIONS /**`、`/api/auth/**`、`/ws`、`/ws/**` | 公开 |
| `POST /api/runners`（跑腿员注册）、`POST /api/payments/callback` | 公开 |
| `/api/bi/**`、`/api/statistics/**`、`/api/ai/**`、`/api/search/**`、`/api/students/**` | ADMIN |
| `GET /api/payments/**` | ADMIN |
| `POST /api/payments` | STUDENT |

## 七、核心业务流程

### 7.1 订单生命周期

```
1. 学生登录 → 我的订单 → 新建订单（选包裹尺寸 → 选取件地址 → 填送达地址与取件码 → 提交）
2. 后端计算金额、生成标题与订单号，落库 status=0，同事务写入 event_outbox，
   并自动生成 payment 记录（pay_status=0）
3. 事务提交后触发两类后续：
   ├─ 事件投递（若配置开启自动派单）→ DispatchConsumer 为订单挑选跑腿员
   └─ 若没派出去（无合适跑腿员 / 开关关闭）→ 订单留在待接单池等人抢
4. 跑腿员在「可接订单」看到 status=0 的订单 → 接单
   └─ CAS 原子更新：UPDATE ... WHERE id=? AND status=0 AND runner_id IS NULL
      affected rows = 1 即抢到；= 0 说明已被别人抢走或已被系统派出 → 返回 409
5. 跑腿员推进状态：1 →（2 取件中，可选）→ 3 配送中 → 4 已送达
6. 学生端收到 WebSocket 推送并刷新 → 确认收货 → 4 → 5 已完成
7. 弹出评分窗（1-5 星 + 标签 + 文字）→ 提交后重算跑腿员平均分
8. 跑腿员释放为空闲、完成单数 +1，收入统计随之更新
```

### 7.2 事件驱动流程（Outbox）

```
业务事务内                                    事务提交后
    │                                            │
    ├─ 更新业务数据（订单 / 支付 / 跑腿员）         │
    └─ INSERT event_outbox (status=PENDING)  ──────┘
                                                  │
                    ┌─────────────────────────────┴──────────────────┐
                    ▼                                                ▼
        提交后立即唤醒投递（毫秒级）                        轮询兜底（默认 1 秒）
        OutboxWakeupListener                             OutboxDeliveryScheduler
                    └─────────────────┬──────────────────────────────┘
                                      ▼
                     claim()：条件更新 PENDING/FAILED → SENDING（行级 CAS，
                     并发投递同一行时只有一个成功，无需额外加锁）
                                      ▼
                             Kafka send → markSent(SENT)
                                      │
                          失败 → 指数退避重试，超 max-retries → DEAD
                                      ▼
                        单个 topic，3 分区，按 orderNo 作 key
                                      ▼
        ┌──────────────┬──────────────┬──────────────┬──────────────┐
        ▼              ▼              ▼              ▼              ▼
      通知推送        ES 同步        自动派单        异常检测        审计日志
   (5 个独立消费者组，各自全量消费；以 (event_id, consumer_name) 幂等表去重)
```

> **为什么提交后要「唤醒」而不是缩短轮询间隔**：出箱表是持久化真相，轮询是可靠性保证；
> 唤醒只是把正常路径的等待从「最多一个轮询周期」降到毫秒级。唤醒丢了也不影响正确性——轮询会兜住。
> 并发调用 `deliver()` 是安全的，因为 `claim()` 是行级条件更新。

### 7.3 自动派单流程

```
ORDER_CREATED 事件
      │
      ▼
DispatchConsumer（开关 dispatch.auto-enabled 关闭时直接返回，
      │           且**不写幂等行**——否则开关期间产生的订单会被永久标记为已消费）
      ▼
DispatchService.dispatch(orderId)
      │
      ├─ 1. 取订单粒度分布式锁 dispatch:order:{orderId}（tryLock 3s / 租约 10s）
      ├─ 2. 读订单，状态必须为 0
      ├─ 3. 读生效中的定价规则得到三项权重（距离 / 评分 / 负载），读不到就用默认值
      ├─ 4. 取所有空闲跑腿员 + 一次查询批量取回各自在途单量（避免 1+N）
      ├─ 5. 逐个打分：距离用 haversine（半径外得 0）、评分为 rating/5、负载为 1 - 在途/并发上限
      ├─ 6. 取最高分；低于 min-score-threshold 则放弃（订单留在池中）
      └─ 7. CAS 落库：UPDATE ... WHERE id=? AND status=0 AND runner_id IS NULL
                        │
             affected = 1 ──▶ 置跑腿员为接单中、写轨迹、发 ORDER_DISPATCHED 事件
             affected = 0 ──▶ 已被抢单者得手，直接放弃（不置忙、不写轨迹、不发事件）
```

> **为什么第 7 步必须是 CAS**：派单在读订单之后、落库之前要完成打分，
> 这段时间跑腿员完全可能用抢单路径把订单抢走。原先的无条件 `updateById` 会把 `runner_id`
> 覆盖成派单选中的人，导致**同一订单两名跑腿员都认为自己持有**。两条路径现在走同一套条件更新，谁先写谁赢。
> 这条有真库并发测试覆盖（`DispatchCoexistenceIT`，30 轮）。

### 7.4 登录认证流程

```
1. 打开前端 → 未登录 → 跳 /login
2. 选角色 Tab 提交 → POST /api/auth/{role}/login
3. 后端校验密码（BCrypt）；失败则计数 +1，15 分钟内满 5 次该账号锁定 → 429
4. 成功则签发 JWT（payload: sub / role / name / iat / exp / ver），
   同时刷新该账号的登录失败计数
5. 前端把 token 与过期时间写入 localStorage（campus_helper_auth），
   请求层统一附加 Authorization: Bearer <token>
6. 每个请求经 JwtAuthenticationFilter 验签并比对 ver 与账号当前版本，不一致即 401
7. 收到 401 → 前端清除本地凭据并跳转登录页
8. 登出 → POST /api/auth/logout → 账号版本 +1 → 该账号全部已签发 token 立即失效
```

### 7.5 会话撤销流程

账号维度的 token 版本号存于 Redis（`TokenVersionService`），JWT 签发时写入 `ver` 声明。
以下操作会使版本 +1，从而让该账号**所有已签发 token**（含其他设备）立即失效：

| 触发 | 入口 |
|---|---|
| 本人登出 | `POST /api/auth/logout` |
| 停用跑腿员 | `PUT /api/runners/{id}`（status=2） |
| 踢跑腿员下线 | `POST /api/runners/{id}/revoke-tokens` |
| 停用学生 | `PUT /api/students/{id}` |
| 踢学生下线 | `POST /api/students/{id}/revoke-tokens` |

> **当前没有「改密码」接口**，所以「改密即全端下线」这个说法**不成立**——简历或演示里不要写。
> 管理员自身没有撤销入口（只能自己登出）。

## 九、关键设计决策

1. **取件码可见性**：学生和管理员始终可见；跑腿员仅在**接单后**可见（未接单时后端会把该字段置空，防止抢单前获取敏感信息）

2. **订单标题**：系统自动生成（包裹数 + 尺寸 + 金额 + 取送地址），仅管理员和跑腿员可见，学生看不到

3. **订单金额**：按包裹尺寸由后端计算（小 4 / 中 5 / 大 8），不接受客户端传入

4. **取件地址**：下拉选项标准化（南三门外卖柜、九斋外卖柜、北门外卖柜、南三门快递站）

5. **评分机制**：1-5 星 + 可选标签 + 自由文本；提交后自动重算跑腿员平均分

6. **实时推送**：WebSocket(STOMP) 在连接帧校验 JWT，principal 绑定为 `{userId}_{role}` 实现按用户定向推送；
   订单列表与详情页**另外保留 2-3 秒轮询作为兜底**（`useRef` 保存最新函数引用，避免 interval 被销毁）

7. **密码存储**：**BCrypt**（`BCryptPasswordEncoder`）。
   v3.0 写的「当前为明文存储」**已不成立**——历史明文口令由 `PasswordMigrationRunner` 在启动时迁移为 BCrypt，
   学生 / 跑腿员登录路径的明文回退分支已移除。
   ⚠️ 唯一遗留：管理员凭据支持 BCrypt，但当前 `.env` 未配 `ADMIN_PASSWORD_HASH`，仍走明文比对兜底（启动时会打 WARN）

8. **CORS**：允许 `http://localhost:*` 与 `http://127.0.0.1:*`，开发与生产无需分别配置

9. **认证与会话**：JWT 无状态 + 账号维度版本号撤销（见 7.5）。
   版本号存在 Redis，读取失败时**放行（fail open）**——避免 Redis 抖动导致全站无法登录

10. **支付闭环**：订单创建时自动生成 payment 记录（pay_status=0）；
    订单状态流转由前端驱动，支付由管理员后台管理；回调接口用 HMAC 验签且签名内容含时间戳，阻断重放

11. **事件不丢**：订单状态变更不直接发 Kafka，而是与业务数据**同事务**写入 `event_outbox`，
    由独立调度器投递。投递失败按指数退避重试，超限转 `DEAD` 并保留现场，可人工介入重放

12. **消费端幂等**：单一 topic 被 5 个消费者组各自全量消费，通过 `(event_id, consumer_name)` 联合主键去重，
    实现「至少一次投递 + 消费端幂等」

13. **缓存策略**：按数据陈旧容忍度分级——定价规则与 BI 看板可缓存（Cache-Aside，分级 TTL + 抖动），
    **订单状态类数据不缓存**（无法容忍陈旧）。写操作经事务提交后事件（`AFTER_COMMIT`）失效缓存，
    而非延迟双删。代价是跨实例依赖 Redis 可用性

14. **派单与抢单并存**：系统派单（多因子评分）与跑腿员抢单（CAS）**操作同一个状态位**，
    由 `DISPATCH_AUTO_ENABLED` 开关决定是否自动派单。派单未命中时订单回到待接单池，
    两条路径的写入都走同一套条件更新，谁先写谁赢

15. **自动生成编号**：订单号 / 跑腿员号 / 支付号均为「前缀 + 时间戳 + 随机数」，保证全局唯一

## 附：已知限制

本文档描述的是当前实现状态，以下限制在面试或对外说明时**不要回避**：

| 限制 | 说明 |
|---|---|
| 无监控告警 | 未引入 actuator，无健康检查端点与 traceId；后台任务失败仅有日志 |
| 订单超时任务无分布式锁 | `OrderTimeoutScheduler` 多副本部署会重复退款 |
| 部分配置项是死的 | `order.timeout.*` 与 `anomaly.*` 共 6 个配置项零引用，阈值硬编码在代码里 |
| 测试仍有缺口 | 订单状态机的完整转移表、权限矩阵的系统性逐条断言未覆盖；前端零测试 |
| 数据库仍用 root 账号 | 未做最小权限收敛 |
| 回调密钥强度 | `PAYMENT_CALLBACK_SECRET` 当前值偏可猜，建议轮换为随机值 |
| 派单与超时任务的事务边界 | `DispatchService.dispatch` 在 `@Transactional` 方法内持锁，锁释放在事务提交之前；派单写入 CAS 化后订单归属的正确性不再只依赖这把锁，但「锁包住长事务」仍需理顺 |
