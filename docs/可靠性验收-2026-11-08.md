## 16 名跑腿员竞争

`CampusHelperApplicationIT.sixteenRunnersCompeteForOneOrderWithoutDuplicateSideEffects` 使用真实服务事务与 MySQL，屏障同时释放 16 个执行者。

断言与实测：成功 1 人；订单归属为赢家；0→1 轨迹 1 条；ORDER_ACCEPTED Outbox 1 条；忙碌跑腿员 1 人。失败者既可能先看到新状态而得到 400，也可能在条件更新处冲突得到 409；本轮没有把它们全称为 409。

```text
EVIDENCE concurrency: callers=16 winners=1 claim-tracking=1 claim-outbox=1 busy-runners=1
```

已有 `DispatchCoexistenceIT` 的 30 轮自动派单与抢单竞争、无竞争派单及提交后唤醒共 3 项同时通过；这个类使用真实 MySQL/Redis，但投递器为替身，不作为 Kafka 链路证明。

## Kafka 暂停、恢复和重复投递

只暂停测试自己创建的 Kafka 容器，finally 保证解除暂停。暂停期间经 HTTP 创建订单，核对订单仍存在，Outbox 进入 FAILED 且 retry_count ≥ 1；恢复后等待同一事件 SENT、4 个启用处理器的去重记录、1 条通知和 ES 文档。

随后额外投递原事件 3 次，再以相同 key 投递不同 event_id 的校验事件。校验事件作为同分区处理进度标记；其通知提交后，数据库通知总数为 2（原始 + 校验），原始事件通知消费者去重记录仍为 1。

```text
EVIDENCE outage: order-committed=1 outbox=FAILED retry>=1
EVIDENCE recovery: outbox=SENT consumers=4 es-document=present duplicate-replays=3 notifications=2(original+fence)
```

测试固定 `dispatch.auto-enabled=false`，避免被本机 .env 的派单开关干扰。自动派单消费者因关闭而不产生去重记录，故此处为 4，不是 5。

## 验收入口修复

- `campus-test.ps1` 显式接收地址、管理员账号和密码，并调用随仓库提供的 `test-api.ps1`。
- 密码不再硬编码；可以通过 `CAMPUS_HELPER_ADMIN_PASSWORD` 注入。缺少密码时直接失败。
- 原生 ES 计数通过当前 Compose 项目的服务名取得；Docker/curl 失败、结构缺失、计数不一致会报错。
- README 增加配置前置步骤、构建启动与凭据说明。

复现：

```powershell
cd backend
mvn test
mvn -Pintegration verify
cd ../frontend
npm ci
npm run build
cd ..
# 已启动 Compose 且设置 CAMPUS_HELPER_ADMIN_PASSWORD 后：
./campus-test.ps1
```

如服务由另一个目录的 Compose 项目启动，设置匹配的 `COMPOSE_PROJECT_NAME`；本轮只读冒烟复用了现有服务的项目名与凭据，没有重建该运行栈或修改业务数据。

## 边界与剩余告警

- 并发测试是正确性竞争测试，不是 QPS、容量或性能承诺。
- 单节点 Kafka、acks=1 不提供多副本耐久性结论；没有声称端到端 exactly-once。
- 本轮验证通知数据库副作用去重，不等于 WebSocket 与所有外部动作均严格一次。
- 全量日志中 Kafka 暂停时的发送超时属于故障注入预期；无 Kafka 的派单/超时测试上下文仍会输出 KafkaAdmin 连接告警，但所有断言通过。已为两个主要集成类增加上下文关闭，避免它们在容器停止后继续后台重试。
- 构建仍提示大包：Dashboard 约 1495 kB、入口约 608 kB（未压缩）。路由已产生独立页面包，但不能称为首屏性能已优化。
- 前端和后端分别构建/测试；本轮没有重新构建生产 Compose 镜像。网页入口冒烟对象是现有本机运行栈，不能用它推定新镜像发布成功。
- 测试数据在 Testcontainers 临时容器内创建，容器由测试清理；没有向现有业务栈新增订单。Docker Desktop 保持运行。
